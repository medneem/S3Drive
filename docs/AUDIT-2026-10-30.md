# Аудит S3Drive — 30 октября 2026 года

## Методика и границы

Проведён статический просмотр Python-модулей GUI, rclone mount, службы Windows,
шифрования и хранения профилей, удаления кэша, RC API, GitHub Actions и тестов.
Проверены механизмы версионирования, упаковки `onefile`, контроль SHA-256
загружаемых rclone/WinFsp, правила релизов и защита административных файлов.

Это аудит **исходников и автоматических тестов**, а не пентест Windows,
не антивирусная экспертиза и не замена испытания с реальным QNAP.

## Исправлено

### 1. Высокий приоритет: некорректный идентификатор профиля

**Проблема:** `Profile.validate()` не проверял `id`, хотя он используется
для имён каталогов кэша, логов, фоновых сессий и службы. Повреждённый либо
преднамеренно изменённый `config.json` мог содержать строку вроде
`../outside`, а также неканонические UUID.

**Исправление:** проверка канонического UUID (включая запрет нестроковых
значений) до любых операций с путями. При загрузке и сохранении запрещены
дубли идентификаторов, в том числе отличающиеся только регистром UUID.
При обнаружении проблемного конфигурационного файла GUI откажется его
перезаписывать, пока пользователь не исправит файл.

### 2. Высокий приоритет: открытые файлы при отключении

**Проблема:** штатные `MountManager.stop()` и `ensure_vfs_idle()` для службы
проверяли только `uploadsQueued`, `uploadsInProgress` и `erroredFiles`,
но игнорировали `inUse`. В то же время кнопка удаления кэша уже
блокировала удаление при открытых файлах.

**Исправление:** все операции штатного отключения используют
`ensure_cache_idle()`, то есть отклоняют остановку при открытых файлах,
невыгруженных записях и ошибках rclone. Неполный ответ RC блокирует
остановку, а не считается подтверждением завершённой синхронизации.

Документация RC: https://rclone.org/rc/#vfs-stats-stats-for-a-vfs

### 3. Низкий приоритет: установка и автоподключение

Уточнён `README_SETUP.txt`: обычное пользовательское монтирование
после перезагрузки нужно подключать вручную, но установленная служба
Windows стартует автоматически и не зависит от запущенного GUI.

## Результаты проверки архитектуры

- Секреты профилей хранятся в DPAPI, не передаются напрямую в аргументах
  командной строки пользовательского rclone.
- Секреты и файлы конфигурации службы находятся в защищённом каталоге
  ProgramData; RC службы требует авторизации и слушает loopback.
- `clear-cache` запрещает удалять кэш при остановленной службе и при
  неподтверждённом завершении VFS-передач.
- Служба Windows не зависит от главного окна; GUI можно закрыть.
- ZIP содержит контрольные файлы `rclone.exe` и WinFsp, скачиваемые
  из официальных релизов с проверкой зафиксированных SHA-256.
- GitHub Actions запускает `unittest discover -s tests -v` **три раза**
  и лишь затем собирает `onefile`.
- GitHub Release не публикуется при обычном push; для выпуска требуется
  ручной запуск с конкретной SemVer-версией.

## Ограничения и что остаётся проверить

1. Провести реальное тестирование `S:` на Windows/WinFsp и QNAP S3:
   копирование, чтение, переименование, удаление и возврат после перезагрузки.
2. Проверить, что открытый через Проводник файл действительно блокирует
   отключение службы, а после закрытия файла отключение успешно.
3. Протестировать аварийное выключение системы с незавершённой загрузкой и
   восстановление сохранённого VFS-кэша после запуска rclone.
4. Проверить права `FileSecurity=D:P(A;;FA;;;WD)` на общем ПК:
   всем локальным пользователям выдаётся полный доступ к S3-диску.
5. Отдельно расследовать поведенческое срабатывание Kaspersky
   `PDM:Trojan.Win32.Generic`: успешные тесты не гарантируют
   отсутствие угроз.
6. При планируемом промышленном использовании добавить подписывание EXE
   и проверку зависимостей на уязвимости. Это не включено в текущий аудит.

**Важно:** три зелёных запуска CI показывают стабильность тестов, но
не подтверждают работу всех сценариев на машине пользователя и не являются
трёхкратной ручной проверкой настоящего S3.
