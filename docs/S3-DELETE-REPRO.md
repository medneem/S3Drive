# Проверка неполного удаления S3-каталогов через rclone mount

## Зачем

30 октября 2026 пользователь удалил через смонтированный Windows-диск
дерево вложенных каталогов. В Проводнике оно исчезло, но Cyberduck всё ещё
видел вложенный объект, а после переподключения каталог снова появился.

В журнале подключения **корня S3** rclone 1.75.2 показывает накопленные
счётчики \`deletedDirs=10\`, \`deletes=0\`. Это не доказывает, что S3
получил удаление файлов: внутри S3 каталоги — виртуальные префиксы.
Строка \`Removing directory\` тоже не подтверждает удаления объектов
из бакета. Конкретный момент удаления в предоставленном фрагменте
не определяется.

## Изолированный E2E в GitHub Actions

Workflow: \`.github/workflows/s3-deletion-e2e.yml\`.

- Windows GitHub-hosted runner с официальным **WinFsp**, установленным
  для теста.
- **rclone 1.75.2** и WinFsp загружаются тем же скриптом, что для
  основного ZIP, и проверяются по закреплённым SHA-256.
- Локальный Python **Moto S3** доступен только на \`127.0.0.1\`;
  реальные endpoint, профили и ключи не используются.
- \`mount_command()\` и \`remote_environment()\` берутся прямо из S3Drive.
- Верификация выполняется через **отдельный S3 API** (boto3) и повторное
  монтирование. Видимость папки в Windows **не считается доказательством**
  успешного удаления.
- Тесты запускаются 3 раза, включая проверку итогового состояния сервера
  после каждого удаления.

### Сценарии

1. Вложенное дерево в **конкретном бакете**; проверка полного удаления
   ключей и сохранения соседнего файла.
2. Тот же сценарий при **пустом поле «Бакет»**, т. е. корневом
   S3-монтировании. Первая папка в корне — именно **бакет**.
3. **Гонка VFS-кэша:** смонтированный диск уже прочитал содержимое
   каталога. Другой клиент создаёт дополнительный файл напрямую через
   S3 API, затем дерево удаляется через диск. Тест обнаруживает
   опасный случай «Windows сообщила об успешном удалении, а ключи
   на сервере остались», включая повторное появление после remount.
   Отказ операции с ошибкой безопаснее ложного успеха.

### Результат запуска 30 октября 2026 (Windows CI №1)

В [GitHub Actions](https://github.com/medneem/S3Drive/actions/runs/41067309181)
сценарии удаления обычного дерева из бакета и из корня S3 прошли.
Сценарий с внешним добавлением файла после чтения каталога **воспроизвёл
неполное удаление в 3 из 3 прогонов**: Windows успешно удалила папку,
но S3 сохранил `stale/album/late.txt`; после повторного монтирования
каталог появился снова. Это воспроизводимая ошибка rclone 1.75.2 + VFS,
не требует настоящего QNAP.

Повторный запуск: [GitHub Actions №2](https://github.com/medneem/S3Drive/actions/runs/41067979937).
Сценарий с устаревшим кэшем **снова воспроизвёл неполное удаление (3/3)**.
При сравнении с `--dir-cache-time 0s` **во всех 3 проверках файлы
на сервере удалялись полностью и папка не появлялась после remount**.

Два базовых сценария удаления тоже прошли 3/3. Интеграционный job
завершился со статусом `failure` намеренно: он проверяет ещё не исправленную
штатную конфигурацию rclone и не маскирует воспроизведённый дефект.

Решение владельца: применить `--dir-cache-time 0s` автоматически
ко всем подключениям S3Drive (служба и пользовательский rclone), без
новых переключателей GUI. Повторные E2E теперь проверяют реальные
параметры `mount_command()` из S3Drive, в том числе корень и отдельный
бакет, а также изменения другим S3-клиентом после чтения папки.
Это целевое исправление доказанного сценария; не гарантия атомарности
удаления при конкурентных изменениях и не испытание настоящего QNAP.
Обновлённой установленной службе требуется обновление командной строки
SCM через остановку и повторное подключение из S3Drive.

### Интерпретация

- Зелёный результат показывает только отсутствие воспроизведения
  на **Moto + WinFsp + rclone** с проверенными сценариями.
- Красный результат с \`REPRODUCED:\` — подтверждённый сценарий
  скрытого оставшегося объекта, **не обязательно ошибка Python GUI**.
- Если установка WinFsp или Moto не удалась, это проблема окружения
  CI, а не результат проверки удаления.
- Поведение QNAP S3 может отличаться от Moto; для окончательного
  заключения нужен отдельный тест против **изолированного тестового
  бакета QNAP**, с явным разрешением владельца. Никогда не запускать
  эти разрушающие тесты против рабочего бакета.

Обычный \`Build Windows\` и публикация релизов не затронуты.
